Building the hypervisor blind

In the OpenSPARC T2 archive the hypervisor (hv) is one source tree for all platforms: shared code in greatlakes/common, with the T1 (ontario) and T2 (huron) parts beside it. ontario/t1_fpga is one build variant of it, a Makefile with the options for OpenSPARC T1 on FPGA boards, meant for Sun's own toolchain; the archive also ships its prebuilt q.bin.

Here the hv from that tree is built with GNU tools and run on QEMU instead of an FPGA. At first there was no way to know the image was right except to boot it: hence "blind".

This is how it went, stage by stage.

  1. Dumb start: swap in Sun's prebuilt ontario/t1_fpga/q.bin for the hv from the T1 archive.

    The console stayed silent, but a QEMU trace showed signs of life: the hv spun waiting for the UART while printing its very first start-up message, ironically PRINT("Alive and well ...\r\n") in main.s This debug build writes to the FPGA's debug UART, which QEMU does not model.

    Once that UART was added to QEMU as a second serial port, the hv began to print its start-up messages. They showed that the hv was being handed wrong values early in boot: the "strand start set" was an address, and the "total physical mem" was garbage.

    Both come from the CPU reset code, so reset.bin had to be rebuilt.

  2. Rebuild reset.bin.

    Built with GCC, reset.s failed in just two ways: old-style (K&R) token pasting in the TRAP() macro, fixed by -traditional-cpp, and missing .register declarations, which the GNU assembler requires and a small wrapper adds.

    The reset code hands the hv a mask of strands to start, 0xffffffff: all (up to 32) strands of a T1. QEMU has one, and Sun's q.bin, built with -DT1_FPGA, waited forever for the other 31. A small patch changed the mask to 1.

    The result is tiny: reset.bin is 768 bytes and comes from one file, reset.s.

    This was a small success: the first SPARC binary built with GNU tools in this project.

    The kit's own hv kept -DT1_FPGA at first. Much later it was dropped: without it the hv has no code that waits for the other strands, so Sun's reset.s now runs unpatched.

  3. Find what the hv wants from the MD.

    The MD had long been the reason Solaris would not boot; now the same MDs, in the T1 format, could not even get past the hypervisor.

    With the new reset.bin the hv ran through its start-up and stopped while parsing the content-version of the hv MD.

    Swapping in Sun's hv MD (S10image/1c1t/legion-hv.md from the T2 archive) made the hv accept it and stop later, on the version check of the guest MD header (1up-md.bin).

    After these two stops the MD was put aside: to see what the hv wanted from it, the hv itself had to be built first.

  4. Build the hv itself without Sun's toolchain.

    The hv's assembly code depends heavily on offsets.h, which gives the offset of each field inside the hv's C structures and the size of each structure.

    The file is not part of the source: the build generates it. Sun's build does it from the debug records of its own compiler, and modern GCC can no longer write those records.

    So the numbers had to come from somewhere else, in a way that could be trusted.

    The answer was to ask gcc itself, and several independent checks against Sun's own build showed its answers were right. The details are on a separate page.

    Only then was the build turned to ontario, the T1. It starts from Sun's legion variant, with a few options switched off for QEMU (README.options).

  5. When the hypervisor finally met its MD.

    With the hv built from source, the work on the MD resumed. The hv MD was redone in the new format, starting from Sun's own configurations in the T2 archive; every value was then set to what the hypervisor actually reads, and md/REFERENCE lists each one with the line of code that reads it. The guest MD was brought up to match.

    The hv did say why it stopped, but not always truthfully: "Missing root node in HVMD" came from a valid MD, and the fault was in the build. So the hv's own debug output was switched on, and the start-up code was followed from the QEMU monitor: where it stopped was compared with the source, to work out what was really missing.

    The new hv first started the unmodified niagara/t1_fpga/openboot.bin from the T2 archive, which still carries the driver for the Legion simulator's disk (see the Forth page).

    At each start it stopped on one property the guest MD still lacked (FATAL: Missing required property …); each was added to the MD, until there was nothing left to name and it reached the ok prompt.

    Three warnings still appear at every start, before the OpenBoot banner:

    WARNING: Unable to connect to Domain Service providers

WARNING: Unable to get LDOM Variable Updates

WARNING: Unable to update LDOM Variable

    They are expected: the guest is an LDoms domain, and there is no control domain at the other end for it to talk to.

  6. On to Solaris 10.

    Solaris 10 was next. Its kernel reads the MD more strictly than OpenBoot, and each panic showed what was still missing (see the MD page). In the end it reached its login prompt from the T1 archive's own disk image, S10image/disk.s10hw2, on the newly built hv, with machine descriptions it accepts. From then on, no firmware from the T1 archive was needed.

Everything so far had been child's play next to what came next: building OpenBoot.
