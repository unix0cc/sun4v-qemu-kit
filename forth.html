Forth-on-SPARC that builds itself: a five-step bootstrap chain

OpenBoot is written in the Forth language and relies heavily on its dictionaries. Two kinds of file take part:

  • a dictionary (.dic): a whole Forth system, as SPARC machine code;
  • the Forth engine, a C program (built from wrapper.c and fsys.c).

Unlike a classical Forth interpreter, the engine has a different purpose: to load a dictionary and jump into it. Once loaded, the dictionary is the running Forth: it can read source files and write a new dictionary.

The kernel, the lowest layer of a Forth system, appears this way: a metacompiler (Forth code itself, fm/meta) compiles the kernel sources (fm/kernel) for the chosen target and saves the result as a new dictionary.

The seed dictionary is forth.dic, a 32-bit SPARC image that ships with the source as a binary, with no source of its own.

forth.dic ─▶ kernel-xref.dic ─▶ forth32-xref.dic ─▶ k32t32-xref.dic ─┐
 shipped      32-bit kernel      host dictionary     the same kernel,│
 root                                                built again     │
┌────────────────────────────────────────────────────────────────────┘
└▶ f32t32.dic ─┬▶ k64t32.dic
   host        │  64-bit kernel
   dictionary  └▶ tokenize.dic
                  FCode tokenizer

The whole flow is in the OBP build flow diagram.

A Forth is built by a Forth, so a chain like this has to start somewhere, and in Sun's original chain that start is forth.dic.

The way to trust such a start is to make the result rebuild itself: the first kernel (kernel-xref.dic) is made by the shipped dictionary, the second (k32t32-xref.dic) by a Forth that grew from the first, and the two come out identical, byte for byte.

Sun's makefile, written about 20 years ago (prudently?), already allows for this: the second kernel may replace forth.dic. The GNU path (TOOLCHAIN=gnu) turns it into a check and stops if the two differ.

The other six dictionaries of the chain are kept in src/obp as well. Each of them is made again on every build, and only forth.dic is read as a seed. They are in the kit to check the GNU path (TOOLCHAIN=gnu): what it builds is compared with Sun's copies.

The engine is built twice: a 32-bit one runs the 32-bit steps, a 64-bit one the rest, including the stand-alone bootprom and the reset code.

The tokenizer (tokenize.dic) is a Forth compiled with Sun's default compiler, the 32-bit f32t32.dic, alongside the 64-bit kernel.

Once the dictionaries are ready, it takes the device-driver sources (*.tok files, also written in Forth, spread across src/obp/obp) and turns them into FCode. If you have read this far, you most likely know what FCode is. If not: FCode is the compact, platform-independent bytecode in which Open Firmware (IEEE 1275) carries drivers: the same driver runs on the Forth kernel of whichever platform loads it, even across architectures (FirmWorks, Plug-In Drivers).

That is what the platform-dependent Forth kernel, the one this chain builds, is for.

For example, the IDE driver ide.tok pulls in a dozen .fth files and ends up as a dropin named class010100, the PCI class code of an IDE controller:

ide.tok, ata/disk.fth, atapi/cdrom.fth, ... (12 .fth in all) ─tokenize.dic─┐
┌──────────────────────────────────────────────────────────────────────────┘
└▶ ide.fc (FCode) ─makedi─▶ dropin "class010100" ─▶ builtin.di ─▶ openboot.bin

makedi wraps every FCode image into a dropin, and makeprom packs the dropins, together with bootprom and the reset code, into openboot.bin.

A dictionary is SPARC machine code, so on a non-SPARC host (the kit has been built on x86_64 and aarch64) the GNU path runs the engine (forth32 under qemu-sparc32plus, forth64 under qemu-sparc64), and makedi and makeprom run under qemu-user too; the rest of the build is native.

The kit also has an experimental entry point that does without forth.dic, based on Mitch Bradley's cforth; many files of the OpenBoot Forth source also carry copyright lines of Bradley Forthware, his company, next to Sun's (for example compilin.fth of the metacompiler).

Why the PCI guest grew in parallel: building a platform to build its own firmware

The seed forth.dic and the engine are SPARC code, and a native build of OpenBoot with Sun's tools needs a Solaris with a disk and a network. The emulated niagara machine had neither, so for more than a month the work on the chain went hand in hand with a PCI prototype of the machine, each needing the other for testing. Fortunately, the OBP image from the T2 archive (niagara2/release/openboot.bin) was usable as it was: it already contained the vpci dropin.
