Building offsets.h without Sun's compiler

Paradoxically, the hypervisor for the T2 platform, huron, was built first from the OpenSPARC T2 archive, retracing Sun's steps for it before repeating them for the real target, T1, ontario.

Why?
Sun left a finished huron build with offsets.h and q, the unstripped ELF version behind q.bin, with the names of functions and variables still in it.
It was a rare piece of luck: for ontario there is only the flat q.bin.
So the method was worked out on a hypervisor that nobody needs here.

The hardest part was producing a correct offsets.h for the assembler. The hv's assembly code reads C structures by fixed offsets and sizes (e.g. CONFIG_MEMSIZE, CONFIG_SIZE, CPU_SCR_INCR). These numbers are not written by hand: offsets.h is generated at build time. Sun's procedure uses its own tool in C, stabs, which extracts them from the debug records of the Sun compiler (cc -xdebugformat=stabs; the blue route in the diagram).

For the first two lines of struct config it fills in the parameters in offsets.h, i.e.:

# offsets.in: the input
config      CONFIG_SIZE
  memsize   CONFIG_MEMSIZE

# offsets.h: Sun's stabs output, for huron
#define CONFIG_SIZE 0x570
#define CONFIG_MEMSIZE 0x8

However, gcc has not supported -gstabs since v13. It does emit DWARF, but at the time a DWARF reader would have been more work.

So another way was needed.

It helped that the SPARC V9 ABI (p. 38) fixes a structure's layout, so gcc and Sun cc should lay out structures alike. That was taken as an assumption. If so, gcc can answer instead of Sun cc: sizeof and offsetof give the same numbers.

genoffsets.py does exactly that (the fourth route in the diagram). The first hv builds used it; now it is an independent test path.

The tool reads the same offsets.in and writes from it a small C file with one question per constant name (CONFIG_SIZE, CONFIG_MEMSIZE, …):
"how big is struct config, and where in it does the member memsize sit?"
The questions are sizeof and offsetof, wrapped in an inline-asm constant. For the same two lines, generated on the GNU path:

# genassym.c: written by genoffsets.py (GNU route)
GENASSYM(CONFIG_SIZE, sizeof (struct config));
GENASSYM(CONFIG_MEMSIZE, __builtin_offsetof(struct config, memsize));

# genassym.s: gcc -S output, each answer is a plain text line
@@genassym@@ CONFIG_SIZE 1392
@@genassym@@ CONFIG_MEMSIZE 8

# offsets.h: collected by genoffsets.py from those lines
#define CONFIG_SIZE 0x570
#define CONFIG_MEMSIZE 0x8

These are the same values as in Sun's offsets.h above.

The numbers come from the very compiler that builds the rest of the hypervisor, so they cannot disagree with it. And since no debug records are read, the tool does not depend on any debug format.

And that turned out to be true: all 1114 numbers that sparc64-linux-gnu-gcc -S answered matched Sun's own offsets.h for huron.

The unstripped q gives a second, independent check: the size of a variable is its sizeof as the Sun compiler laid it out, padding included. Had the two compilers padded this structure differently, the sizes would not match. The global variable config is an instance of struct config, so the size nm shows is its sizeof:

$ sparc64-linux-gnu-nm -S q | grep ' config$'
000000fff041da80 0000000000000570 B config

That is 0x570, exactly the CONFIG_SIZE that gcc computed.

That is not enough: a wrong number passes silently through assembling, linking and even running. So every function of the new build was also compared with Sun's build of the same function. At this scale (654 functions, in the output of two different compilers) that is tedious for a human, so it was left to an AI agent:

  1. sparc64-linux-gnu-nm -S on the huron ELF q file, which kept its symbols, lists the functions with their addresses and sizes.
  2. sparc64-linux-gnu-objdump -d disassembles each function's address range in Sun's original q and the same function in the new object file.
  3. sed strips what cannot match: addresses, encoded bytes, comments and branch targets (the new objects are not linked yet).
  4. What is left is compared line by line: SAME or DIFF for each function.

For example, start_master in main.s keeps the memory base and size in config:

    ...
    sub     %g1, %g5, %g6     ! %g6 - global config

    ! set global memory base/size
    stx     %i0, [%g6 + CONFIG_MEMBASE]
    stx     %i1, [%g6 + CONFIG_MEMSIZE]
    stx     %i3, [%g6 + CONFIG_STRAND_STARTSET]
    stx     %i4, [%g6 + CONFIG_PHYSMEMSIZE]

Sun's compiled q holds the same stores with the offsets filled in:

$ sparc64-linux-gnu-objdump -d q | grep -B1 -A2 'stx  %i1, \[ %g6 + 8 \]'
  fff00094c8:  f0 71 a0 00  stx  %i0, [ %g6 ]
  fff00094cc:  f2 71 a0 08  stx  %i1, [ %g6 + 8 ]
  fff00094d0:  f6 71 a0 80  stx  %i3, [ %g6 + 0x80 ]
  fff00094d4:  f8 71 a5 20  stx  %i4, [ %g6 + 0x520 ]

CONFIG_MEMSIZE is 8, as gcc said.

Of the functions compared, 377 came out identical. 112 differ, and none of them points to a wrong structure offset: they use other instructions for the same value, have placeholders for addresses in objects that are not linked yet, or are C code from a different compiler. Another 165, mostly C functions, differ in size and were not compared line by line.

For example, in hcall_tod_set the constants ENUM_HVctl_res_guest, HVCTL_RES_STATUS_RES and GUEST_GID are all 0. gcc assembles the first line as clr, Sun's cc as sethi %hi(0); the register ends up zero either way:

source (hcall_core.s)gccSun's cc
set ENUM_HVctl_res_guest, %g5clr %g5sethi %hi(0), %g5
stuw %g5, [%g3 + HVCTL_RES_STATUS_RES]st %g5, [%g3]st %g5, [%g3]
ldx [%g6 + GUEST_GID], %g5ldx [%g6], %g5ldx [%g6], %g5
