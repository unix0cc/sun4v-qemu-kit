The machine descriptions: 1up-hv.bin and 1up-md.bin

Each Machine Description (MD) is a binary directed acyclic graph (DAG), described by Sun in 2005 (FWARC 2005/115): a simple guest can find what it needs, such as the number of CPUs, by walking the list of nodes, without following the graph.

Little has been published about working with it. A Solaris guest reads only its own domain's MD; the guest MDs are built by the LDoms Manager from the platform description supplied by the firmware, and the user configures domains, never the MD itself.

So in practice the MD is a black box, and opening it is where this project started.

The first three weeks went to watching live kernels under a debugger, Solaris kmdb, to see how different OS releases consume the MD (#1, #2, #3). That work became the md project.

Sun's LDoms ecosystem was built on big-endian SPARC, and so were its MD tools, mdgen (compiles an MD from text) and mdlint (checks the result). Making them independent of byte order (tested on little-endian hosts, x86_64 and aarch64) exposed bugs, for example a byte-swap branch that tested the OS instead of the actual endianness. Initially, the prototype kit mdbuild built MDs with them; they are the first-generation versions, from the OpenSPARC T1 hypervisor release.

Looking at the OpenSPARC T2 MD configuration files showed that their format differs from the one in the OpenSPARC T1 archive and is much richer: the T1 hypervisor MD is a small graph of three nodes, while T2 MDs have dozens.

Several of those nodes, the cpus and memory containers and the cache hierarchy, are what the kernel debugging above had shown to be missing, and what mdbuild had been adding to the T1 MDs by hand.

The hypervisor from the T1 archive, which works with QEMU, does not accept these MDs. So the next step was to read the hypervisor source in the OpenSPARC T2 archive. There came a surprise: it still builds the ontario platform, which is a T1.

So the OpenSPARC T2 archive could give a hypervisor for the T1 machine QEMU emulates.
